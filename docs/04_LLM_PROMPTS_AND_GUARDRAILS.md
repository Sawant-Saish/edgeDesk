# LLM PROMPTS & ANTI-HALLUCINATION GUARDRAILS

## 0. Answering your original question directly

**Do you need to train an LLM? No.** You need:
1. An API key for one existing LLM provider (Anthropic or OpenAI) — this is the only "AI setup" required.
2. Good prompts + strict output schemas (this file).
3. Deterministic code (plain JS) for anything that must be *consistent* — skill-gap math, course scoring. LLMs are used only where judgment/language is genuinely needed: reading messy resume text, writing a human explanation, and roleplaying a conversation.

This split is the actual engineering answer to "how do I stop it from hallucinating": **don't ask the LLM to do arithmetic or maintain a database — ask it to read language and write language, and validate everything else in code.**

## 1. `shared/llmClient.js` — the one function everything calls

Responsibilities:
- Takes `{ systemPrompt, userPrompt, responseSchema, maxRetries = 1 }`.
- Calls the LLM with `temperature: 0` for extraction/scoring tasks (deterministic-as-possible), higher (e.g. 0.7) ONLY for the negotiation roleplay reply itself.
- Instructs the model to return **raw JSON only, no markdown fences, no preamble** — put this in every system prompt that expects structured output.
- Parses the response; runs it through `validateSchema.js` (e.g. using `ajv` or `zod`).
- If invalid: retries once with the validation error appended to the prompt ("Your last response failed validation because X. Return corrected JSON only.").
- If still invalid after retry: throws a typed error (`LLMValidationError`) that the controller catches and turns into a `422`. **Never falls back to returning the unvalidated/partial output.**

## 2. Prompt: Resume skill extraction (F1)

System prompt (fixed, not user-editable):
```
You extract skills from resume text. You may ONLY use skill names from this closed list: {skillTaxonomy list of displayNames}.
Do not invent skills that are not in this list. If the resume mentions a skill not in the list, ignore it.
For each skill you find, give a confidence score 0-1 and the exact sentence/phrase that justifies it.
Return ONLY valid JSON matching this shape, nothing else:
{ "skills": [{ "skillId": "...", "confidence": 0.0, "evidenceSnippet": "..." }], "yearsExperience": 0 }
If you are not confident about a skill, do not include it rather than guessing.
```
User prompt: the raw extracted PDF/pasted text (truncate to ~6000 tokens; if longer, chunk and merge — flag this as a v2 concern if resumes are long).

**Guardrail:** after the LLM responds, cross-check every returned `skillId` against `skillTaxonomy.data.js` in code. Drop any that don't match exactly (do NOT fuzzy-match silently — a near-miss like "React.js" vs "react" should map via an explicit alias table you control, not LLM guessing).

## 3. Prompt: Gap explanation text (F2)

This is cosmetic only — never gates logic.
```
Given this matched skills list and this missing skills list for the role "{roleName}", write a 1-2 sentence
encouraging but honest explanation for a junior freelancer. Do not mention any skill not in these two lists.
Return ONLY: { "explanationText": "..." }
```

## 4. Prompt: Negotiation roleplay (F4)

System prompt (persona-locked, rebuilt fresh each session from seeded data — never let the LLM invent the budget):
```
You are roleplaying as a client named {persona.name}. Your hidden budget range is ${min}-${max} — never reveal
this number directly, negotiate toward the lower end. Your objection style is: {objectionStyle}.
The project brief is: {briefText}.
Stay in character. Keep replies under 60 words. Do not break character to give the user meta-advice —
that happens only in the end-of-session scorecard, generated by a separate prompt.
Never mention that you are an AI.
```
**Guardrail:** the budget numbers and brief come from `projectBriefs.seed.json`, injected into the prompt as data — the model is told them, not asked to invent them. This keeps sessions fair/comparable and stops budget drift across turns.

## 5. Prompt: Negotiation scorecard (F4, separate call from roleplay)

```
You are an impartial negotiation coach, not the client. Given this full conversation transcript and the
client's actual hidden budget range (${min}-${max}), score the freelancer's performance.
Return ONLY JSON matching:
{ "finalAgreedPriceUSD": 0, "clarityScore": 0, "boundaryScore": 0, "professionalismScore": 0, "summaryText": "..." }
Base finalAgreedPriceUSD strictly on what was explicitly agreed in the transcript; if no explicit number was
agreed, set it to null and say so in summaryText.
```
**Guardrail:** running the scorer as a *separate* call with a *separate* system prompt (not the same context as the roleplay) avoids the client persona "grading its own performance" and leaking character bias into the score.

## 6. General rules for every prompt in this system

1. Every system prompt that expects structured output explicitly states the exact JSON shape and says "ONLY valid JSON, no other text."
2. Every structured output is validated in code before being trusted (schema validation is not optional, not a "nice to have" — it is the guardrail).
3. Nothing the LLM outputs is treated as a source of truth for a fixed vocabulary (skill names, course data, role requirements) — those always come from seeded/static data.
4. Temperature is `0` for anything extraction/scoring; only the roleplay reply itself uses a higher temperature, and even that is turn-capped and persona-locked.
5. Log every prompt+response pair (strip PII from logs where possible) during development — this is how you'll debug hallucination if it happens, and it's a fast senior-dev habit worth having from day one.
